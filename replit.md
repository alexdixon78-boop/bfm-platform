# Brighter Future Mediation - CRM & Case Management Platform

## Overview

Brighter Future Mediation is developing a professional web-based CRM and case management platform for UK family mediation services. The platform aims to streamline operations, enhance client management, and provide robust case handling capabilities. Key features include secure login, comprehensive Enquiries and Cases modules, a robust Role-Based Access Control (RBAC) system, user and client management, mediator qualifications tracking, client portal invitations, structured confidential notes, and an audit logging system. The platform prioritizes scalability, maintainability, and a user-friendly interface inspired by HubSpot, focusing on high growth and market leadership in online mediation services.

## User Preferences

- Branding: Grey primary (HSL 0 0% 40%), sage green accent (#a7baa4 / #5a7d58), dusty rose/coral accent (#dcae96 / #b8825a), warm cream backgrounds

- Logo: Actual BFM logo PNG images (coral left circle, sage green right circle, grey BFM letters, "BRIGHTER FUTURE MEDIATION" text)
- Font: Aptos (body), Agrandir (headings) - loaded via CDN
- Style: Professional, warm, accessible
- Tagline: "Fully accredited online mediation specialists. Supporting you from conflict to resolution."
- Accreditation: FMC, College of Mediators, FMA, and Ministry of Justice logos displayed as links on the large-screen login page
- Dashboard: 8 stat cards (New enquiries, Outstanding enquiries, Active cases, MIAMs this week, Mediation sessions this week, Overdue payments, Awaiting client action, Awaiting BFM action). Superadmins and subadmins can use them as quick links to Enquiries, Cases, Appointments, Finance, and Tasks; other internal roles see static cards. Outstanding enquiries counts unclaimed, non-closed intake enquiries and links to the Enquiries Unclaimed filter.
- Admin reports: `/reports` is the dedicated superadmin/subadmin reporting dashboard with last-12-month default filters, total cases, cases by stage, total sessions, upcoming sessions, closure reason reporting, and basic session summary charts. Revenue charts use paid invoice totals from the finance ledger and are omitted from subadmin responses and UI. Manual case revenue remains a single GBP amount on each case and is visible/editable only to superadmins.
- Client records: firstName, lastName, DOB, email, phone (+44), gender, ethnicOrigin, NI number, disability, additionalNeeds, confidential, full address, MIAM mediator and allocated mediator per party
- Lead sources: canonical values live in `LEAD_SOURCES` in `shared/schema.ts`, including `Website`; API docs must render from that source of truth rather than hard-coded copies.
- Online only service: no room/office references in appointments
- **Service Catalogue**: The baseline catalogue includes MIAM, mediation, court/documentation, and package services. Eight additional services are inserted idempotently by migration `0055_service_catalogue_expansion` and the seed data. Service names used by booking and mediation-session workflows remain unchanged. Service Catalogue users with Edit access can create, edit, and activate/deactivate services; only superadmins can permanently delete an unlinked service, and deletion is refused when it has any linked mediator assignment/approval/schedule, appointment, invoice, or invoice line item. Each baseline service has an immutable baseline name, so a deletion tombstone prevents seed or a repeat migration from recreating it even after it has been renamed; explicitly adding the same original name through the Service Catalogue clears that tombstone. Linked services must be made inactive instead.

## System Architecture

The platform is built with a modern web stack: React, Tailwind CSS, shadcn/ui for the frontend, Express.js for the backend, and PostgreSQL with Drizzle ORM for the database.

**Core Architectural Decisions & Features:**

- **Role-Based Access Control (RBAC)**: Supports superadmin, subadmin, staff, mediator, client, and contractor roles. The Settings page exposes configurable Internal Role Access for Subadmin, Staff, Mediator, and Contractor across the shared business-area catalogue: Overview, Enquiry Management, Case Management, Appointment Management, Client Records, Mediator Management, Contractor Management, Finance, Court Forms, Reporting, Team Management, Audit & Compliance, Service Catalogue, and WhatsApp Communications. Dashboard/Reporting/Audit edit actions are unsupported. Legacy Documents, Contacts, and Settings keys remain internal compatibility entries and cannot be submitted through the permission API. Superadmin permissions are fixed. Client portal access is also fixed by product policy (Dashboard, Mediation, Appointments, and My Contacts, with Documents inside each mediation case) and is documented in a separate read-only Settings card rather than the configurable matrix.
- **Permission Persistence & Propagation**: `GET /api/permissions` always returns the complete canonical role/section matrix with stored overrides merged over defaults. `PUT /api/permissions` is superadmin-only, accepts validated changed configurable rows, performs one conflict-aware bulk upsert, records one before/after audit entry, and returns the canonical matrix directly. Bootstrap and migration `0042_repair_permission_defaults` add missing defaults without overwriting configured values. The authenticated notification WebSocket publishes role-targeted `permissions_updated` events so affected clients refetch permissions immediately.
- **Role-Specific Settings**: `/settings` is fixed by role rather than controlled by the permission matrix. Superadmins receive system, payment, calendar, and RBAC panels; Subadmins receive the organisation-calendar panels; Mediators receive personal-calendar settings; Staff and Clients are excluded. Mediator Google/Outlook OAuth carries a validated first-party return target for Settings, Appointments, Dashboard, or the completed onboarding calendar step, so success, cancellation, and expected failures return to the originating screen with safe plain-language messages instead of browser-rendered JSON. A successful authorization remains connected when initial sync or webhook setup is delayed; the UI explains that BFM will retry through the existing workers. Mediators can disconnect their selected provider from Settings after confirming that imported unbooked availability will be removed while existing appointments remain unchanged.
- **Authentication System**: Secure login, logout, password management, rate limiting, and client portal invitation system. Pending mediator, staff, subadmin, and contractor accounts can complete setup through their onboarding invitation or a valid password-reset link; superadmins and subadmins with Mediator Management edit access can also set a mediator password manually from the mediator listing, which activates pending mediator accounts and clears onboarding tokens without exposing the password in API responses. Logout destroys the server session and clears the session cookie; the frontend also cancels active authenticated queries, clears the previous user's React Query data and transient session storage, restores the `["/api/auth/me"]` query to `null`, and redirects to `/login` with history replacement. Protected APIs continue to enforce the server session and return `401` after logout, including on refresh or browser-back navigation.
- **Self-service account profiles**: Every signed-in role can open `/my-profile` from the header to change their own name or password and upload a profile picture. `PATCH /api/account`, `POST /api/account/password`, and `POST /api/account/photo` use the current session identity; password changes require the current password. Mediator account names are stored separately in `users.account_display_name` and do not replace the mediator directory name until reviewed. Profile pictures are validated PNG/JPEG/WebP files up to 5 MB, stored under `profile-images` through the configured local/S3 storage driver, and served through `/uploads/profile-images/:fileName` (proxied from the private bucket in S3 mode). Mediator account pictures appear in the signed-in header immediately; a separate request must be approved before the picture is copied to the mediator profile.
- **Mediator profile change requests**: Mediators can propose changes to visible staff-controlled factual fields from their existing detail tabs. Requests are stored in `mediator_profile_change_requests` by migration `0056_account_profiles`; their values remain pending until a Superadmin or Subadmin reviews them through the mediator detail page. Internal decisions, hidden fields, and Payment stay admin-controlled. Existing mediator direct edits and bio review continue. Account name changes for mediators create first/last name requests for the directory profile.
- **Per-service mediator role qualification**: Mediator role qualification is now stored on each `mediator_service_types` assignment rather than used as one profile-wide scheduling value. Superadmins/subadmins choose Unclassified, Observer, Co-mediator, or Lead mediator beside every selected service in Add/Edit mediator and the mediator profile Service offering tab. `PUT /api/mediators/:id/services` accepts `{ services: [{ serviceTypeId, mediationRoleQualification }] }`; the legacy `{ serviceTypeIds }` payload is still accepted and stores those services as Unclassified. Migration `0061_per_service_mediator_role_qualification` adds `mediator_service_types.mediation_role_qualification`, backfills existing service assignments from the old profile-level qualification, and creates missing assignments for active mediators with currently approved service approvals so approval-only legacy services retain their Lead/Co/Observer eligibility. The legacy `mediator_profiles.mediation_role_qualification` remains readable for compatibility but is no longer the source of MIAM or mediation-session eligibility.
- **Case Access And Client Data Isolation**: Shared case authorization classifies each request as `admin`, `operational_staff`, `full_mediator`, `session_co_mediator`, `miam_only_mediator`, `session_observer`, `client_party`, or `none`. Staff with Case Management View receive all-case list/detail scope through `operational_staff`, while Edit authorizes ordinary case operations; Staff do not become administrators and invitation secrets remain redacted. Admins, case leads, and session leads retain full operational case access. Accepted co-mediators and observers can find the case in the Cases listing and receive an allowlisted case-detail view with Overview, Clients, Appointments, MIAM Record summaries, and Mediation Sessions; co-mediators additionally retain read-only ordinary Documents. Their case context contains both parties' names, roles, email addresses, and phone details plus MIAM record/approval/suitability/completion/validity status, but excludes MIAM answers, addresses, demographics, financial disclosure, finance/payment data, safeguarding, domestic-abuse data, confidential notes, communications, and operational audit data. Their appointments and sessions are limited to exact accepted assignments. Accepted co-mediators have the same non-admin Mediation Sessions actions as that session's lead, while observers remain read-only. Pending, declined, removed, and unrelated session participants gain no case access. MIAM-only mediators are restricted to their assigned parties and MIAM workflow. Client case list/detail responses use explicit allowlisted DTOs containing case workflow metadata, mediator display name, the authenticated client's own party/profile data, and that party's MIAM validity summary; they exclude the other party, safeguarding and intake disclosures, internal/confidential notes and markers, referral and closure internals, revenue, staff/audit metadata, and invitation/token fields. Confidential notes, communication ledgers, proofing, finance, and other operational case records are restricted to admins, operational Staff, and full assigned mediators unless a narrower client-owned workflow explicitly allows access. Sensitive actions remain explicitly restricted, including permission administration, integration/secret settings, WhatsApp environment settings, legacy Client import, manual case revenue, confidentiality changes, administrative reassignment, hard-delete/restore operations, and Subadmin/Superadmin account management. Staff with Team Management Edit may manage Staff peers only.
- **Case Confidentiality Marker**: `cases.confidential` is a manually controlled operational marker with `BOOLEAN NOT NULL DEFAULT false`, introduced by `0037_case_confidential_flag.sql`. Superadmins and subadmins may change it only through `PATCH /api/cases/:id/confidential`; each change records audit and case-activity entries. When a case is newly marked confidential, the CRM creates an amber in-app awareness notification for admins and for mediators who already have full operational case access (case lead or mediation-session lead). Removing the marker does not create a new alert. Safeguarding concerns never enable this marker automatically, and it is independent of `safeguardingConfidential`, staff-only confidential case notes, the Confidentiality + Agreement to Mediate form, and client/party-level confidentiality fields. Admins and full-access mediators see a read-only `Confidential` badge wherever they may already view the case; co-mediators and observers do not receive this marker, and clients never receive the case flag. Enquiry list/detail responses derive `caseConfidential` from the linked `convertedCaseId` case and return `false` when no linked case exists.
- **Dynamic Intake Follow-Ups**: New first-contact records may create a dynamic intake follow-up rather than the legacy fixed Day 5/Day 10/weekly path. The UI keeps **Next follow-up in (days)** and the canonical Europe/London **Follow-up date** synchronized in both directions, defaults to tomorrow, and supports an optional valid start/end time window. Assignment is optional: selected active staff share one all-day or timed BFM calendar event and receive the idempotent due alert; leaving assignment blank creates an immediately visible admin-wide task, skips calendar scheduling, and sends one notification-bell alert to active superadmins/subadmins when due. Existing fixed chains remain legacy-compatible until intake closes.
- **Enquiry Acknowledgement Template**: New-enquiry acknowledgements use a MIAM-focused acknowledgement template whose subject ends with the linked case reference. The shared flow automatically creates or reuses a Client A MIAM booking link, renders a "Book MIAM Appointment" button, and may include best-effort upcoming MIAM date/time snippets that deep-link to the booking page. `/enquiries` Add New Enquiry and Mail Inbox conversion both use this same template when a valid email and linked case context are available. MIAM information is linked through the Google Drive folder only; no attachment is sent.
- **Client-A-only booking intake details**: The public booking-token response derives the party role server-side. Only Party A receives, sees, validates, and persists Brief description, Children’s details, and How did you hear about BFM? Brief description and the BFM referral source remain required for Party A; Children’s details is optional. Every non-A party receives none of these values and server-side validation/persistence ignores forged submissions, while existing historical MIAM and demographic values remain unchanged.
- **Client Portal MIAM Self-Service**: Logged-in clients can start their own first-time MIAM booking from their case Summary card in Overview or My Details. The client-owned endpoint creates a secure booking token only for the authenticated client's own party, sends no email, and redirects into the existing `/book/:token` flow. It is blocked when the client already has an active MIAM hold/future booking, a currently valid MIAM, or should use the repeat-MIAM renewal flow.
- **Safeguarding Auto-Claim**: When a superadmin or subadmin records either safeguarding gate outcome on an unclaimed intake case, the case is automatically claimed by that user in the same update. Existing claims are preserved; both admin roles may work across claims without silently reassigning ownership.
- **Shared Safeguarding Gate UI**: The intake workflow uses one shared, status-aware safeguarding panel in both the full `/enquiries/:id` intake workspace and the safeguarding-only `/cases/:id` case overview card. Pending decisions use a calm amber treatment, clear decisions use green confirmation styling, and active concerns use red/destructive styling. Raising a new safeguarding concern creates a red in-app awareness notification for admins and for mediators who already have full operational case access; editing notes while the case is already in concern status does not duplicate that alert. The panel exposes the current status badge, short status-specific guidance, safeguarding notes, `No safeguarding concern`, `Raise concern`, and `Notify Rebecca` actions. Superadmins and subadmins can use these controls across claims; Staff remain claim-bound. `Notify Rebecca` remains a separate explicit escalation action: it stamps `rebeccaNotifiedAt`, creates the existing red admin task, records audit/activity entries, and sends a best-effort email to Rebecca's active superadmin account without exposing safeguarding notes in the email body.
- **Case Overview Safeguarding Gate**: Superadmins/subadmins see only the shared safeguarding panel on `/cases/:id`. Claim, first-contact, chase, and intake closure operations remain in the full `/enquiries/:id` intake workspace; case closure uses the separate case close control.
- **Enquiry Intake Closure**: Closing intake from `/enquiries/:id` is terminal for the enquiry chase workflow. It completes/suppresses open Day 0, Day 5, Day 10, and ongoing intake follow-up tasks, makes the chase status read-only history with no further chase required, and still does not close the linked case `status`.

### Dynamic intake action and follow-up history

- The enquiry-detail card is named **Claim and next intake action** (it retains its existing `section-intake-claim-first-contact` test identifier). It renders one current action in priority order: safeguarding decision, claim ownership, Day 0 first contact, Day 5, Day 10, ongoing weekly follow-up, no action required, or a terminal intake/safeguarding-stop reason.
- Day 0 is recorded exactly once. Once recorded, its original timestamp, canonical contact method, and optional notes are shown as immutable read-only history above the current action; the Day 0 form is never re-enabled. The same card immediately advances to its open Day 5 task, then Day 10, then one weekly task at a time.
- Day 5, Day 10, and weekly entries require a valid contact method and non-empty notes. Staff may record an upcoming task early, while the card continues to show its scheduled due date and `Upcoming`, `Due today`, or `Overdue` timing. The latest completed follow-up remains visible in **Claim and next intake action**, with a newest-first collapsible list of every earlier completed follow-up and a link to the full chase-status section; the current open action stays directly below that history. The card reads this allowlisted history from `GET /api/cases/:caseId/intake/tasks`, backed by the authoritative notification task records. Superadmins and subadmins may read it across claims, Staff remain claim-bound, and mediator/client access is denied. An initial history-load failure disables follow-up submission and offers a retry; a later refresh failure retains the previously loaded history with a stale-data warning. Completed entries remain read-only and cannot be reopened through the card.
- Day 0 and later chase transitions are atomic: the current task completion, successor reuse/creation, case/enquiry status update where applicable, audit log, and case-activity write commit together. Task-update notifications are published only after commit. Repeated, retry, or concurrent completion attempts return HTTP `409` without creating duplicate tasks, audit records, or activity records.
- Migration `0038_intake_first_contact_transition` adds the persisted Day 0 method/notes fields and repairs historical intake records idempotently: it restores canonical Day 0 values from audit history, completes stale Day 0 reminders, creates only missing eligible Day 5 tasks, and guards repair audit records. Malformed legacy audit JSON is parsed exception-safely and cannot erase bootstrap-populated Day 0 method/notes while the earliest timestamp is still repaired. It does not send email, webhook, or realtime notifications.
- **External API Integrations**: Superadmins have a dedicated `/api-integrations` page for server-to-server API documentation and key management. API keys are shown once at creation, stored only as SHA-256 hashes, do not expire automatically, and remain valid until a superadmin revokes them; revocation takes effect immediately and raw keys cannot be recovered later. The first integration is `POST /api/public/integrations/website-enquiries`, intended for the external website backend only, using `Authorization: Bearer <api_key>` or `X-API-Key`. The website enquiry API accepts the submitted `leadSource` instead of forcing it to `Website`; website origin is tracked in audit/notes as `Website API`. Optional UTM fields and `websitePageUrl` are website metadata, not CRM enquiry form fields. The second integration is `POST /api/public/integrations/calendly-consultations`, intended for direct Calendly webhooks; it verifies `Calendly-Webhook-Signature` with `CALENDLY_WEBHOOK_SIGNING_KEY`, creates records only for `invitee.created`, and treats `invitee.canceled` as an audited no-op in v1. The API page shows Calendly signing-key configured/not-configured status only; the actual signing key is never displayed and must be managed through environment secrets. It also shows a read-only WhatsApp / Meta Cloud API setup card backed by `GET /api/whatsapp/settings`, including the public webhook URL and configured/missing indicators for the required environment-managed credentials; secret values are never returned or displayed. The configured Meta app must also be subscribed to the configured WABA through `/{WABA_ID}/subscribed_apps`; Meta's dashboard test webhook alone does not prove that real customer messages will be delivered.
- **WhatsApp webhook and outbox reliability**: Signed webhook responses retain the existing `processed` array and add safe message/duplicate/status counts for request logs and audit diagnostics without logging phone numbers, names, message bodies, secrets, or raw payloads. Outbound sends use atomic five-minute `nextAttemptAt` leases, and a non-overlapping worker processes up to 20 due rows after startup and every minute. Network, `408`, `429`, `5xx`, and recognised Meta transient/rate-limit errors retry on 1/2/4/8/16-minute backoff for at most six total attempts; permanent errors become failed immediately. Only successful sends and terminal failures create conversation-message rows, so intermediate retries do not duplicate the conversation history.
- **WhatsApp enquiry Flow**: `docs/integrations/whatsapp-new-enquiry-flow.json` is the source-controlled definition of the published static `ENQUIRY_FORM`. It completes directly into the existing WhatsApp `nfm_reply` webhook and therefore must not declare `data_api_version`, `routing_model`, `data_exchange`, or a Flow data endpoint. The deployed Flow ID and initial screen remain environment-managed through `META_WHATSAPP_ENQUIRY_FLOW_ID` and `META_WHATSAPP_ENQUIRY_FLOW_SCREEN`; publishing a replacement Flow requires updating the ID because Meta does not allow published Flow JSON to be edited in place. WhatsApp Flow enquiries preserve the submitted `leadSource`/`leadSourceOther` answer and tag the intake channel separately through `contactMethod = "WhatsApp message"` plus `metadata.source = "whatsapp"`. Their WhatsApp success reply is queued as soon as the enquiry, case, and reference exist; duplicate detection and automatic acknowledgement email continue asynchronously and log failures without delaying the client-facing reference.
- **Case-scoped WhatsApp workspace**: A telephone number still owns one organisation-wide WhatsApp conversation, but `whatsapp_messages` now carries its own `caseId`, `partyId`, `clientId`, classification, and assignment source. Explicit case sends and verified private-note messages are always scoped; ordinary inbound messages auto-scope only for one active client case or one case with message context in the previous 24 hours, and otherwise remain unassigned for manual review in the global inbox. When an inbound phone number uniquely matches a client who has multiple active cases, the message retains the matched `clientId` with `multiple_active_cases_unassigned` but deliberately leaves `caseId` and `partyId` blank rather than choosing the latest case. Existing message rows are backfilled only from their existing conversation case and are never redistributed heuristically. The case Communications tab has `History` and admin-only `WhatsApp` views. The workspace requires Superadmin, or Subadmin with Case Management View plus WhatsApp Communications Edit; it enforces case-party membership, a valid mobile, the case `No WhatsApp or voicemail` restriction, recorded party opt-in, Meta's 24-hour free-text/media window, and approved templates outside the window. Party opt-in/opt-out history, approved Meta templates, outbound media validation/upload state, and individual message delivery/read/failure results are durable. The case WhatsApp tab and global `/whatsapp` inbox now share a production chat workspace with WhatsApp-style inbound/outbound bubbles, delivery/read/failed status treatment, clear 24-hour-window guidance, and an approved-template composer that disables free text outside Meta's customer-service window while still allowing staff to choose and preview approved templates when free text is available. Selected templates render a pre-send preview from saved Meta `components`, including variables, footer/buttons, language/category, missing-value prompts, and header-media requirements. Admins can also send approved booking shortcuts from case detail: `bfm_miam_booking` from a client summary card creates/reuses that party's secure MIAM booking link, and `bfm_mediation_session_booking` sends a recipient-specific mediation-session response link from the Mediation Sessions proposal row. Both shortcuts preview resolved variables first and still enforce case WhatsApp permissions, opt-in, phone validity, `No WhatsApp or voicemail`, and approved-template sync. The saved approved Meta template catalogue is exposed with last-sync/count/stale metadata; staff can manually run template sync when the list is stale or empty, and the app does not auto-sync on page open. Template synchronization retains the last successful catalogue during Meta outages. New uploads and existing case documents are limited to five files and 10 MB each, checked by actual file signature/type, and uploaded to Meta only after validation. These files are not malware-scanned.
- **Private WhatsApp case notes**: The Existing Case WhatsApp action first tries to match the inbound WhatsApp phone number to exactly one CRM client with exactly one active case. A clean phone match skips the case-reference step; first use still asks for the registered/account email, emails a hashed six-digit OTP, and then stores the verified WhatsApp contact/client/party/case tuple. Later Existing Case selections from the same WhatsApp phone skip OTP only while that stored tuple still matches the same active phone-resolved case; ambiguous clients, multiple active cases, closed/archived cases, or `No WhatsApp or voicemail` fall back to explicit verification. When phone matching is unavailable, the reference step accepts either the bare case reference or a canonical party-suffixed reference such as `BFM-2026-0024-B`; when a suffix is supplied, the client email must belong to that party role, while eligible administrator and full-mediator account matching remains case-wide. During the unverified reference, email, and OTP steps, exact greeting/menu commands such as `hi`, `hello`, `menu`, `start`, or `restart` cancel the verification draft, reset the conversation to the standard start menu, and do not treat partial matches such as email addresses as commands. OTPs expire after ten minutes, allow five attempts, enforce a 60-second resend interval, three sends per hour per phone/identity, and ten identity lookups per hour per phone. A completed note can contain text and/or up to five validated attachments. Draft/verification message bodies and raw payloads are masked from inbox APIs and never enter the general Communications ledger; completion creates one content-free `Private WhatsApp note received` Communications ledger entry, one content-free Recent Activity entry, and a content-free notification. Submitting clients see only their own notes; full-access case/allocated/session lead mediators and administrators see all; Staff, co-mediators, observers, and MIAM-only mediators receive no private-note content or metadata. The main case-detail response supplies `privateNotesAccess`, so a case client always sees the Notes tab while server-side list/download policy still restricts them to their own submissions. Only Superadmin can redact completed text or attachments. Inbound media is downloaded, limited to 10 MB, checked by actual signature/type, stored under a private local/S3 prefix, and served only from authenticated `no-store` download routes. Attachments are not malware-scanned; invalid type/size is blocked, transient download/storage failures use bounded retries, and exhausted failures can be requeued by an administrator. Draft media is cleaned up when drafts expire or are cancelled.
- **User & Mediator Management**: Administration of system users and mediators, including service qualification tracking.
- **Mediator Role Qualification**: `mediator_profiles.mediation_role_qualification` stores one global `lead`, `co_mediator`, `observer`, or `unclassified` qualification (default `unclassified`). Eligibility is hierarchical: lead-qualified mediators may fill any session role, co-mediator-qualified mediators may co-mediate or observe, and observer-qualified mediators may only observe. Superadmins and subadmins can edit the field; the mediator owner can view it read-only, and profile-field audit logging records every change. The retired per-case-type Solo / co matrix remains in the database for legacy history but is no longer shown or validated. Migration `0043_mediator_role_qualification` backfills active mediators with a current approved `Mediation Sessions` service approval to `lead`, leaving all others unclassified.
- **Confidential Case Complaints**: Case complaints are a dedicated domain, separate from case notes, activities, communications, ordinary tasks, and the existing mediator-profile `mediator_complaints` register. Authenticated clients linked as a party, full-access mediators, subadmins, staff using an exact case reference, and the singleton superadmin can submit. Only the superadmin receives the complete record, named subject, evidence, internal investigation history, and case-level Complaints tab; a submitter receives an allowlisted projection containing the complaint/case references, public status and dates, released updates, open clarification requests, and final outcome/response. Staff exact-reference intake deliberately returns no case, party, client, or mediator details. Each submission creates an append-only event history and a private `complaint_review` reminder task with `caseId = null`; generic task mutation/completion is blocked and complaint actions alone control complaint status. Acknowledgement and response targets are calculated at 10 and 30 England/Wales working days, including standard/substitute, Easter, and explicitly maintained exceptional holidays. The FMC three-month field is advisory and never blocks active, closed, or older-case submissions. Withdrawal, duplicate marking, audited redaction, and closure preserve the original record; product hard-delete is not provided. Complaint receipt/update email is best-effort, contains no complaint content, and cannot roll back the portal record. The user service rejects creation/promotion of another superadmin and demotion/deletion of the bootstrap superadmin; migration `0040_case_complaints` preflights duplicates and installs the partial unique role index.
- **Mediator Service Calendar Capture**: Per-service approval rows now carry Google Calendar event metadata (`calendar_start_at`, `calendar_end_at`, `calendar_title`, `calendar_notes`, `calendar_google_event_id`, `calendar_updated_at`) so approved services can be scheduled independently and surfaced in the mediator detail/dashboard views.
- **Service Proof Review Updates**: The applicant update link flow now shows the stored rejection reason, blocks submission when a requested service is marked required but has no proof, and records request/review notifications for audit purposes.
- **Mediator Service Approval Revocation**: Superadmins/subadmins can revoke an approved live mediator service from the mediator detail Service offering tab with a required reason. Revocation records audit/review metadata, creates the existing proof-request task/email flow, blocks future booking eligibility by moving the approval out of approved status, and preserves existing proof files, schedule slots, calendar metadata, and appointments for history.
- **Mediator Service Offering Sync**: When an applicant is converted to a mediator, every applicant service approval row now links into the live `mediator_service_types` list so the mediator profile service offering reflects all requested services; booking eligibility still depends on per-service approval status.
- **Mediator Service Offering Read Path**: The mediator services endpoint now returns the union of live service-type assignments and linked service approval rows, so the profile page reflects all requested services immediately even before a separate manual sync.
- **Mediator Service Offering Requirements and Listing**: Mediators and subadmins must provide a concrete mediation role qualification (Observer, Co-mediator, or Lead mediator) and at least one active service before saving; superadmins may save an incomplete profile, including an `Unclassified` qualification or no selected service. Mediation types is optional. `GET /api/mediators` includes `mediationRoleQualification` with an `unclassified` fallback, and the Mediators listing shows the readable qualification label.
- **Superadmin Mediator Profile Editing**: Superadmins may save incomplete mediator profile sections without required-field or linked completion checks (including WTA details and Credentials child records). Entered formats and time ranges are still validated, the account email remains required for login, and an incomplete public bio may be saved as a draft but cannot be submitted or approved.
- **Client Management**: Person-centric client views with cross-party field propagation.
- **Confidential Case Notes**: Categorized operational notes with audit trails, restricted to admins and full assigned mediators. They are separate from the general `cases.confidential` marker and are never exposed to clients, MIAM-only mediators, or session observers.
- **Client Portal Invitation System**: Facilitates client registration via time-limited invite tokens.
- **Audit Logging**: Comprehensive, immutable logging of critical system actions. ## API Conventions

- All endpoints live under `/api/*` and are defined in `server/routes/*.routes.ts` (one file per resource). Each file exports an Express `Router`; `server/routes/index.ts` imports and registers them all, and also runs the DB bootstrap (see below).
- Layering: route → service (`server/services/*.service.ts`) → repository (`server/repositories/*.repository.ts`) / `storage.ts` → Drizzle.
- **Auth**: session-based (cookie sessions via `express-session` + `connect-pg-simple`, session store in Postgres). `requireAuth` (`server/middleware/auth.ts`) checks `req.session.userId`, loads the user onto `req.user`, else 401.
- **Session behavior**: protected APIs require a valid `connect.sid` cookie backed by the Postgres session store. `GET /api/auth/me` is called by the frontend during startup; `401 { message: "Not authenticated" }` is normal when no user is logged in or when a manual request omits cookies. `401` means no valid session/user was found; `403` means the user is authenticated but lacks RBAC permission. Every `/api` response receives `Cache-Control: no-store`, `Pragma: no-cache`, and `Expires: 0` so protected payloads are not restored from browser/intermediary caches. Frontend API calls use `credentials: "include"`; curl/manual API tests must preserve cookies explicitly.
- **Permissions**: `requirePermission(section, "view" | "edit")` (`server/middleware/permissions.ts`) enforces the canonical role/section matrix. Ordinary Staff navigation and APIs use the matching business-area View/Edit grant; explicit inline role checks remain only for sensitive or destructive exceptions. Client access and eligible Settings roles are fixed policies rather than matrix-controlled.
- **Validation**: Zod schemas defined next to the tables in `shared/schema.ts` (via `drizzle-zod` `createInsertSchema` + extensions) are used to validate request bodies.
- **Complaint APIs**: `POST /api/complaints` performs role-aware case-ID/exact-reference submission. `GET /api/complaints` and `GET /api/cases/:caseId/complaints` are superadmin-only; `GET /api/complaints/:id` returns either the full superadmin DTO or the submitter allowlist; `GET /api/complaints/mine` lists only the authenticated submitter's safe records. Complaint-specific status, note, deadline-extension, escalation, clarification-reply, redaction, receipt-retry, and authenticated evidence-download endpoints live in `server/routes/complaint.routes.ts`. Unauthorized complaint reads deliberately return 404 to avoid confirming a complaint exists.
- **Legacy client import APIs**: the Clients page exposes a superadmin/subadmin `.xlsx` workflow backed by `POST /api/clients/legacy-import/inspect`, `/preview`, and `/commit`; all three additionally require `clients:edit`. Requests carry the workbook as base64 JSON, but the server never persists the source file. Inspect returns friendly, sectioned mapping metadata and excludes credential, bank, payment, Stripe, authentication, integration-payload, and token columns. The wizard shows operation-specific loading states, source-to-CRM mapping, selection-based duplicate actions, unique-match bulk linking, safe bulk skipping for prior imports, open-row legacy case counts, and a searchable paginated record confirmation. Possible-duplicate review explains each exact matching rule in plain language and compares the matched workbook person's name, date of birth, email, and phone beside every CRM candidate without selecting a resolution. Preview reparses and normalises the selected sheet, reports placeholders and exact duplicate candidates, counts records whose reviewed legacy status is exactly `open`, and returns a fingerprint. Prior-import matches are skip-only in the UI and remain protected by the commit conflict check, so retained legacy history cannot be imported twice. Commit reparses and rechecks the workbook hash, prior imports, duplicate state, reviewed resolutions, formulas, and uniqueness before an all-or-nothing transaction. During commit, selected legacy rows with status `open` create fresh `Active` BFM cases at stage `Enquiry`, using a new BFM case reference while storing the old `custom_case_id` as `cases.legacyCaseNumber` with `legacySourceSystem = owner_old_crm`; Client 1/Client 2 become parties A/B when imported or linked. These imported cases show a Legacy badge and legacy case number in Case Information, and no enquiries, portal users, appointments, notifications, emails, first-contact tasks, or automatic progress changes are created. `GET /api/clients/:id/legacy-history` requires administrator client-directory access and returns only that client's allowlisted, read-only legacy history plus any linked BFM case reference; no legacy data is exposed through client portal, case, or enquiry APIs.
- **Errors**: services throw errors with an optional `status`/`statusCode`; the global `errorHandler` (`server/middleware/error-handler.ts`) returns `{ message }` JSON with that status (500 default). 404s return `{ message: "... not found" }`.
- **Enquiry acknowledgement delivery**: manual CRM entry, `/enquiries` Add New Enquiry, Website API, Calendly, WhatsApp, and Mail Inbox conversion all use the shared enquiry workflow. The authenticated `POST /api/enquiries` route responds once its transactional CRM records are created, then performs duplicate detection and automatic acknowledgement email delivery in the background. Delivery status remains on the enquiry and can be retried manually; SendGrid requests time out after 10 seconds so a provider stall cannot hold that background work indefinitely. Public Website API and Calendly requests retain their existing synchronous side-effect behavior.
- **Persistent intake follow-up**: after the Day 10 chase, an open case receives a weekly persistent follow-up task until closure. The scheduler maintains one open intake follow-up at a time and does not create the standard chase when safeguarding is a concern.
- **Pagination**: list endpoints accept `page`, `limit` (max 100), `search`, `status`, `sortBy`, `sortOrder` query params.
- **Public token routes**: some endpoints are intentionally unauthenticated and gated by time-limited tokens, webhook signatures, generated links, or server-to-server API keys instead (booking links, demographic form links, client portal invites, onboarding, GDPR consent, public mediator/contractor application links, Stripe/Calendly/WhatsApp webhooks, website enquiries API). `/healthz` is public for ALB/ECS health checks.
- Endpoint groups (route file ↔ URL prefix): auth, dashboard, enquiries, cases, users, mediators, contractors, clients, permissions, parties, audit-logs, service-types, availability, appointments, booking, demographics, notifications, case-activities, miam-records, onboarding, google-calendar, case-filter-presets, representatives, client-representatives, mediator-profiles, mediator-applicants, mediator-pipeline, mediator-application-links, contractor-pipeline, contractor-application-links, reports.

## Database Schema Overview

- **Source of truth**: `shared/schema.ts` (Drizzle ORM, PostgreSQL). For production-like databases, use committed migrations: update the schema, run `npm run db:generate`, review the generated SQL, commit the migration under `migrations/`, then apply it with `npm run db:migrate` against each target database. Both commands load `.env` and then resolve runtime configuration, including `DATABASE_URL` from AWS Secrets Manager when `CONFIG_SOURCE=aws`. If a SQL migration is hand-written or renamed, it must also be registered in `migrations/meta/_journal.json`; Drizzle's migrator reads the journal and will skip unregistered `.sql` files. Hand-written migrations must also keep the latest `migrations/meta/<index>_snapshot.json` aligned with `shared/schema.ts`, or the next generation will recreate already-recorded schema changes.
- **`db:push` is local-only**: `npm run db:push` is a development/prototyping escape hatch. Do not run it against production, staging, Replit deployment DBs, or any database where data loss matters. If Drizzle asks to truncate a table, drop/delete a table, or remove a column, choose **No, abort** and treat it as schema drift that needs a separate audit.
- **Bootstrap pattern**: normal server startup does not run schema DDL or data backfills. Legacy idempotent `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements and backfills live in `server/db-bootstrap.ts` and run only through `npm run db:bootstrap`. Use this for legacy setup/backfill support, not as the primary release migration workflow. `shared/schema.ts` remains the canonical definition — keep bootstrap SQL in sync when it intentionally supports fresh/legacy environments.
- **Schema drift handling**: do not bundle drift cleanup into feature migrations. Known drift candidates such as the connect-pg-simple `session` table, `parties.user_id`, and missing unique constraints must be audited individually, checked for existing data/duplicates, and either represented in `shared/schema.ts` or documented as externally managed before cleanup.

## Background Jobs

All jobs are in-process `setInterval`/`setTimeout` timers started in `server/app.ts` after the server binds (no external cron). Each has a re-entrancy guard flag.

- **Google Calendar auto-sync** — every 15 min (first run 30s after boot): syncs every connected mediator's calendar; audit-logs each sync; flags `invalid_grant` for re-auth.
- **Internal task calendar sync/reminders** — every minute (first run 10s after boot): processes versioned upsert/delete jobs with leases and retry/backoff, sends transactionally de-duplicated in-app reminders to current assignees, and every 15 sweeps reconciles provider deletions/edits back to CRM-authoritative event data. CRM writes are retained during provider outages; Autoscale wake-up means reminders are near-time rather than exact-minute.
- **Calendar task preview and cancellation** — selecting a calendar task opens a read-only workspace with its schedule, assignees, safe linked-record action, and lifecycle history. Superadmins and subadmins with Case Management Edit can cancel any open internal task with an optional reason; cancellation is retained as terminal task history, removes the calendar schedule, and never changes the underlying workflow. Recurring tasks can cancel one occurrence or that occurrence and all future outstanding occurrences.
- **Manual task assignment and recurrence**: The Tasks calendar editor creates one independently completable task per selected active assignee. Superadmins may include mediators and optionally link one case through a bounded search over case reference, client names/emails, and linked mediator emails; case-linked choices are restricted to mediators with existing case access, plus the superadmin's own account when the case has no lead mediator. Subadmins retain staff-only creation. Migration `0053_task_series` adds recurring series and task occurrence identity. Daily/weekly/monthly series use Europe/London dates, include weekends, clamp short months, and generate calendar events through a rolling 12-month horizon via the task-calendar sweep. Future occurrences remain `scheduled` and enter the open task queue and notification bell on their London calendar date. Series may have an optional end date; superadmins can edit one occurrence, replace this-and-future, or stop future occurrences without changing completed history. Staff and subadmins receive BFM Google calendar invitations at their account email; mediators use their active connected Google/Outlook provider or a BFM email invitation fallback. Calendar delivery failures remain retryable without removing CRM tasks. Apply `0053_task_series` before deploying the application version that runs the series sweep.
- **BFM calendar health check** — sweep every 15 min, actual Google probe throttled to ~1/24h (first run 60s after boot): pings the shared BFM mailbox calendar; notifies admins (in-app + email) on failure. Toggleable from Settings.
- **Google token refresh probes** — every 15 min sweep, ~6h throttle per account (first run 90s after boot): cheap token refresh for BFM + each mediator; flips dead tokens to `needs_reauth` and notifies.
- **Boot backfill (one-time, 5s after boot)**: flags Google-connected mediators missing write scope.
- **Appointment expiry + follow-up escalation** — every 5 min: expires unpaid `hold` appointments past their hold window (audit-logged) and escalates overdue follow-up tasks (reminder emails via SendGrid to assignee or admins).
  Note: jobs only run while the server process is up; on Autoscale deployments the process can be scaled to zero when idle, so timers pause until the next request wakes it.

FROM notifications n
JOIN cases c ON c.id = n.case_id

- **AWS IAM role**: the server must use an attached IAM role. Do not set AWS access keys in `.env`, PM2 config, shell profiles, or committed files. Required permissions are `secretsmanager:GetSecretValue` for the app secret, `ssm:GetParametersByPath` only when using Parameter Store, and `kms:Decrypt` only when those values use a customer-managed KMS key.
- **S3 credentials are separate from DB credentials**: S3 access is separate from `DATABASE_URL`; local runs with `STORAGE_DRIVER=s3` must have AWS credentials available through an IAM role, AWS profile/default provider chain, or the local fallback `ACCESS_KEY` / `SECRET_KEY`. Prefer IAM roles on AWS/ECS and never commit AWS keys.
- **Recommended secret/config layout**: store sensitive values as a JSON object in Secrets Manager at `dev-secret`; optionally store non-secret values under Parameter Store path `/bfm/dev/app/config/`. When not using Parameter Store, put all required runtime keys in the Secrets Manager JSON. The server only requires bootstrap env values: `CONFIG_SOURCE=aws`, `AWS_REGION`, and `SECRETMANGER_NAME`; `AWS_SECRETS_MANAGER_SECRET_ID` remains a backward-compatible fallback and `AWS_PARAMETER_STORE_PATH` is optional.
- **AWS secret keys**: `DATABASE_URL`, `SESSION_SECRET`, `GOOGLE_CLIENT_SECRET`, `CALENDAR_WEBHOOK_SECRET`, `SENDGRID_API_KEY`, `CALENDLY_PAT`, `CALENDLY_WEBHOOK_SIGNING_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `XERO_CLIENT_SECRET`, `XERO_WEBHOOK_KEY`, `META_WHATSAPP_VERIFY_TOKEN`, `META_WHATSAPP_APP_SECRET`, `META_WHATSAPP_ACCESS_TOKEN`.
- **AWS config keys**: `NODE_ENV`, `PORT`, `APP_URL`, `BASE_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_REDIRECT_URI`, `SENDGRID_FROM_EMAIL`, `ADMIN_NOTIFICATION_EMAIL`, `CALENDLY_ORGANIZATION_URI`, `XERO_CLIENT_ID`, `XERO_DEFAULT_ACCOUNT_CODE`, `XERO_DEFAULT_TAX_TYPE`, `XERO_DEFAULT_BRANDING_THEME_ID`, `META_WHATSAPP_PHONE_NUMBER_ID`, `META_WHATSAPP_BUSINESS_ACCOUNT_ID`, `META_WHATSAPP_DEFAULT_TEMPLATE`, `META_WHATSAPP_GRAPH_VERSION`, `META_WHATSAPP_ENQUIRY_FLOW_ID`, `META_WHATSAPP_ENQUIRY_FLOW_SCREEN`, `BFM_CALENDAR_EMAIL`, `LOG_LEVEL`, `STORAGE_DRIVER`, `S3_UPLOAD_BUCKET`, `S3_UPLOAD_REGION`, `S3_UPLOAD_PREFIX`.
- **Docker/ECS**: the production Docker image uses a Node 20 multi-stage build, exposes container port 5000, and runs `npm run start`. `.env`, `uploads/`, `node_modules`, and `dist` must not be copied into the image. ECS supplies runtime env vars and IAM task-role credentials; no AWS access keys are baked into the image. Detailed ECS + S3 instructions live in `docs/deployment/ecs-s3.md`.
- **Run process**: install Node 20 or use the Docker image, run one app process initially because in-process background jobs would duplicate across multiple app processes.
- **Reverse proxy / ALB**: terminate HTTPS at Nginx, ALB, or equivalent and proxy to the app port (`PORT`, default 5000). Use `/healthz` for ALB/ECS health checks. Session cookies become secure automatically in production/AWS mode and Express trusts the proxy. For local HTTP Docker smoke tests, set `SESSION_COOKIE_SECURE=false`; for AWS/ECS behind HTTPS, omit it or set it to `true`.
- **External callback URLs**: set `APP_URL` and `BASE_URL` to the AWS HTTPS CRM URL. Public auth/action links generated by the server use the shared `APP_URL`-first, then `BASE_URL`, runtime helper after AWS Secrets Manager/Parameter Store bootstrap has populated `process.env`. Register the same domain in Google OAuth redirects, Stripe webhooks, Calendly webhook subscriptions, and Meta WhatsApp webhooks.
- **Uploads**: local development can use `STORAGE_DRIVER=local`, but ECS must use `STORAGE_DRIVER=s3` with a private S3 bucket. Mediator service proof links keep the existing `/uploads/mediator-service-approvals/:fileName` URL shape; in S3 mode the backend proxies those files from S3. Case documents are different: direct `/uploads/case-documents/*` URLs are intentionally blocked for both storage drivers and callers must use the authenticated document-ID download endpoint. Complaint evidence uses `private-uploads/complaint-attachments` locally (outside the statically mounted `uploads` tree) and the separate private `complaint-attachments` S3 prefix in hosted environments. Raw `/uploads/complaint-attachments/*` access is blocked as defense in depth; only the authenticated superadmin attachment-ID endpoint may stream a non-redacted file, with `no-store`, `nosniff`, and attachment disposition headers. Complaint requests allow at most five PDF/JPEG/PNG files, 10 MB each and 25 MB decoded total, validated by extension, declared MIME, decoded size, and file signature.
- **Private WhatsApp rollout order**: apply migrations `0058_private_case_notes` and `0059_case_whatsapp_messaging`; grant the Meta token template-read and media permissions; deploy the application/API and workers; run `POST /api/whatsapp/templates/sync`; then enable case messaging and the Existing Case automation. Monitor ambiguous/unassigned inbound volume, template synchronization failures, outbox age, delivery failures, media validation/download/storage failures, exhausted attachment retries, and expired-draft cleanup. Private note and communication-only media live under private local/S3 prefixes and must never be mounted as static content. The accepted deployment model performs size/signature validation but no malware scanning.

## Case Proofing Workflow

- **Source of truth**: `case_proofing_items` stores case-level proofing queue rows for session summaries, Draft Financial Schedules, Financial Disclosure Checklists, Court Forms, and other client-facing documents. Existing tasks and notifications remain the action/reminder layer.
- **Review cycles**: `case_proofing_item_cycles` stores immutable Review cycle history for each proofing item. The Proofing list still shows one current row per source item; repeated proofing of the same source increments Review cycle N and is shown in the detail history, not as duplicate list rows.
- **Version vs Review cycle**: Version labels are reserved for true content versions, currently the Draft Financial Schedule version history. Other repeated proofing passes use Review cycle labels so admins do not confuse workflow resubmission with document versioning.
- **Review actions**: admins can approve, return-to-mediator with comments, or withdraw a proofing item from the Case Details Proofing panel. Returned items create a mediator action task and remain visible to admins.
- **Strict client release**: Proofing approval by a Superadmin or Subadmin is the exclusive release point for proofing-managed client documents. Post-session approval only queues a confirmed Draft Financial Schedule for Proofing; the schedule PDF is generated or released to the client Documents tab only when its Proofing item is approved. Each later schedule review cycle receives its own idempotent PDF identity so amended schedules cannot reuse a prior cycle's released PDF; only a hidden legacy PDF may be reused for the initial migrated cycle. Direct document review cannot set a document to reviewed/client-shared. Each document-producing approval creates an idempotent green in-app notification linking to the Documents tab for every relevant portal user: all case clients for case-level documents, or only the owning client for party-specific documents. Metadata-only approvals do not notify. Generated court forms are saved as pending PDFs and are not emailed/released before approval.
- **Audit trail**: approval, return comments metadata, withdrawal reason metadata, and client release are recorded through case activity and audit logging without exposing sensitive financial values.
- **Ageing**: proofing ageing is derived from submitted time, not stored: green for 0-2 working days, amber after 3 working days, and red after 5 working days.
- **Backfill**: migration/bootstrap logic creates proofing rows and initial Review cycle 1 rows for historical session summaries, Draft Financial Schedules, Financial Disclosure Checklist items, court form generations, and case documents; reviewed/shared records backfill as approved and submitted/ready-for-review records backfill as awaiting review.

The library seeds 42 existing `email.service.ts` senders plus court-form PDF delivery as published system templates, the earlier portal/MIAM compose defaults, and 66 indexed entries from `02BFMclienttemplatesREVIEW160926v2.docx` as drafts. ## Running Locally

Copy `.env.example` to `.env`, keep `CONFIG_SOURCE=local`, and fill in real values (database, session secret, Google OAuth, SendGrid). Then install dependencies (`npm install`), create/update the schema (`npm run db:migrate` and, for legacy bootstrap/backfill support, `npm run db:bootstrap`), seed baseline records (`npm run db:seed`), and start with `npm run dev`. Fresh database seeding creates only the baseline Rebecca superadmin login (`rebecca@brighterfuturemediation.co.uk` / `admin123`), RBAC permissions, and service types; it does not create sample enquiries, cases, clients, parties, mediators, or availability records.

### Auth/session curl testing

Use a cookie jar when testing protected APIs manually:

```bash
curl -i -c /tmp/bfm.cookies \
  -H "Content-Type: application/json" \
  -d '{"email":"...","password":"..."}' \
  http://localhost:5000/api/auth/login

curl -i -b /tmp/bfm.cookies \
  http://localhost:5000/api/auth/me
```

Check the login response for `Set-Cookie: connect.sid`. Unexpected `401` after login usually means the request did not send `connect.sid`, `SESSION_SECRET` changed, the app is pointed at a different `DATABASE_URL`, the session expired/missing from Postgres, or secure-cookie settings are being tested over plain HTTP. Local HTTP Docker smoke tests can set `SESSION_COOKIE_SECURE=false`; AWS/ECS behind HTTPS should omit it or set it to `true`.
